# Implementation Plan: EPYHIA — An Agency Staffed by Agents

**Branch**: `docs/epyhia-agency-spec` | **Date**: 2026-08-02 | **Spec**: [spec.md](./spec.md)

**Input**: Feature specification from `/specs/001-epyhia-agency/spec.md`

## Summary

An agency staffed by agents: one plain-language client brief goes in; a deployed website, a
marketing pack (landing copy, 3–5 posts, launch email, launch video + vertical cut), and a
Stripe test-mode checkout come out. Every action that deploys, charges, sends or publishes
passes through one Action Gate that is the sole holder of external credentials and the sole
place approval, idempotency, retry and audit live.

Technically: FastAPI `web` and a `worker`, two Fly processes running **one image**, communicating
through a `tasks` table. Five PydanticAI agents whose model tier follows the shape of the work
(Opus plans, Sonnet writes, Haiku checks and wires) and whose pipeline is fixed in code — the
Strategist parameterises the stages through a versioned brand doc rather than composing a graph
of its own devising. Everything client-specific lives in one `briefs.payload` column and the
brand doc derived from it; nothing client-specific may appear in source, prompts, constants or
fixtures, and CI proves it by scanning the prompt tree against tokens harvested from the
fixtures themselves.

Two decisions carry more weight than the rest, both inherited from `DESIGN.md`: **no action
reaches `succeeded` without an independent probe of the world**, and **every idempotency key
derives from the brief hash and never from generated bytes**. Phase 0 resolved eleven items
`DESIGN.md` left open — most consequentially what actually counts as a numeral per artifact kind
([research.md R5](./research.md)), which is the difference between a grounding check that works
and one that gets switched off in week two.

**Terminology map** — the spec speaks implementation-agnostically; each pair below is one
concept, not two: the spec's *brand identity record* is the **brand doc**; its *instruction
version* is the **`prompt_version`**; its *deduplication key* is the **`idempotency_key`**;
its *publication* is the **`deploy` action**.

## Technical Context

**Language/Version**: Python 3.13; Node 22 for the console build and Remotion render

**Primary Dependencies**: FastAPI · PydanticAI V2 (`2.22.0`, pinned) · SQLAlchemy 2.0 + Alembic ·
Logfire `4.39.0` · Remotion `4.0.503` (pinned) · Vite, React, TanStack Router/Query, Tailwind,
shadcn/ui · Auth0 · Jinja2 · `uv` / `ruff`

**Storage**: Postgres on Neon. One database for state, audit, orders and artifacts. Artifacts
in `bytea` behind one `ArtifactStore` interface — deliberately not object storage, to avoid a
fourth credential inside the gate and to keep artifact writes transactional with the task row
that produced them (`DESIGN.md` §5.4).

**Testing**: `pytest` + `pytest-asyncio`. PydanticAI `TestModel` / `FunctionModel` for the crew.
**CI must not need an API key**, and the gate's tests must not need an agent, a credential or a
network.

**Target Platform**: Fly.io — one Docker image (Python 3.13 + Node 22 + headless Chrome), `web`
and `worker` as separate `[processes]`, `release_command = "alembic upgrade head"`. Locally,
`docker compose up` (Postgres + Mailpit + web + worker).

**Project Type**: Web service with an operator SPA, an agent worker, and two non-Python
toolchains (console, Remotion). Single deployable image.

**Performance Goals**: **Deliberately unconstrained for run duration.** Nothing in the
architecture trades anything away for run latency — the video render is a queued `tasks` row
rather than a request-path operation, so a slow render costs throughput, not correctness. The
only user-facing latency is the buyer's, covered by SC-009: zero operator interaction between
the buy button and Stripe's form.

**Constraints**:

- No `temperature` / `top_p` / `top_k` on any call — removed on Opus 5 and Sonnet 5; a
  non-default value returns 400. Steering happens through prompting.
- The Web Builder's calls must stream (~64K `max_tokens`). Non-streaming truncates into
  syntactically plausible HTML that would then be deployed.
- `UsageLimits` is token-denominated. There is no dollar ceiling; dollars are derived from
  `RunUsage` through an effective-dated four-rate `pricing.yaml`.
- The app must **start** without Stripe or Vercel credentials and fail only at the specific
  gate action, with `credential not configured: <provider>`.
- Prompt-cache minima differ by model (512 / 1024 / 4096) — a cost anomaly, not an error.

**Scale/Scope**: One operator, many briefs. Multi-tenancy, tenant isolation, role separation and
operator-editable approval policy are explicit non-goals. Ten tables, five agents, seven gate
action types, one approval tier, one audit trail.

| Principle | Verdict | Basis |
|---|---|---|
| **I. Client Data Never in Code** | PASS | The spec's FR-059/FR-060 restate the invariant, and the whole of `briefs.payload` + brand doc is the parameterisation path. Nothing planned puts a client value anywhere else. |
| **II. Design-First, Sequenced Build Order** | PASS | `DESIGN.md` is treated as the record; this plan cites it rather than re-deciding. Implementation follows §12 build order — gate at step 2, before any agent. |
| **III. Fixed Pipeline, Tiered Agents** | PASS | Pipeline fixed in code (FR-013); tiers by work shape; per-agent "may never" enforced by toolset construction (FR-042). |
| **IV. Action Gate Governs All Egress** | PASS | FR-033–FR-043 cover credential sole-holding, the lifecycle with no `executing → succeeded` edge, execute+verify per adapter, and durable approval. |
| **V. Idempotency by Brief Hash** | PASS | FR-044–FR-048, including the two counter-intuitive rules (deploy key excludes site bytes; memo is a cache allowed to miss). |
| **VI. Grounding Before Opinion** | PASS | FR-004–FR-006, FR-016, FR-022 — deterministic check ahead of any model, closed derivation set, gate refuses `deploy` on `flagged`. |
| **VII. Simplicity, Surgical, Goal-Driven** | PASS | Phase 0 records assumptions rather than silently picking; no speculative abstractions introduced. |

**No violations. No entries in Complexity Tracking.** Phase 0 proceeded.

### Post-Phase 1

Re-evaluated against the generated artifacts, looking specifically for places where the design
work *introduced* a violation the spec did not have.

| Principle | Verdict | What the design added, and whether it holds |
|---|---|---|
| **I** | PASS | Every contract file was written to be client-blind and says so: [brief.schema.json](./contracts/brief.schema.json) and [brand-doc.schema.json](./contracts/brand-doc.schema.json) fix the *schema* while all contents vary; [quickstart.md](./quickstart.md) names no business anywhere and reads every expected value from the run's own rows. R2's alias is derived from `brief_hash`, so even the URL is not authored. **The one thing to keep watching**: the brief fixtures. R10's check derives its token set from them, so a fixture with a placeholder name silently weakens the check — the test asserts each fixture yields a non-empty token set for exactly that reason. |
| **II** | PASS | [research.md](./research.md) is split into inherited vs. decided-here precisely so no `DESIGN.md` decision is restated in a second voice. Nothing in Phase 1 contradicts `DESIGN.md`; the two deferrals (Remotion process split, message-history replay) are named as deferrals with their seams located. |
| **III** | PASS | [agent-io.md](./contracts/agent-io.md) makes each boundary a property of what the agent is *handed*: the Strategist's toolset is `write_brand_doc` + `enqueue_tasks` and nothing else; the Reviewer's inputs exclude the run transcript; the task set is fixed in code, not returned by the Strategist. |
| **IV** | PASS, and strengthened | [action-gate.md](./contracts/action-gate.md) pins the ordering §4.4 only implied — the durable row exists **before** `ApprovalRequired` is raised (R7), and the worker releases its lease at the pause. Two guarantees were moved out of code and into the schema: `succeeded ⇒ evidence IS NOT NULL` as a CHECK constraint, and the `deploy`-on-`flagged` refusal as a gate precondition rather than an agent responsibility. |
| **V** | PASS | Key table carried verbatim into [data-model.md](./data-model.md). `agent_cache` has no FK and is documented as droppable, with the reason it is *allowed* to be droppable (no gate key derives from generated bytes) stated on the table itself so a future change cannot make it load-bearing by accident. |
| **VI** | PASS, and made concrete | R5 is the substantive Phase 1 addition: per-kind extraction scope, and a `content`/`style` split in [video-props.schema.json](./contracts/video-props.schema.json) so an on-screen value cannot be placed where the checker does not look. R6 enumerates the closed derivation set including the currency-label case — **with no FX conversion anywhere**, since inventing a rate would be the fabrication the check exists to prevent. |
| **VII** | PASS | Nine tables and one new one (`sink_posts`) beyond `DESIGN.md` §5.4's list, justified by R4. No configurability was added that the spec did not ask for; the one new knob (per-`kind` lease interval, R8) exists because the video render's minutes-long lease and an IO-bound task's cannot share a value. |

**No violations. Complexity Tracking remains empty.**

Two things this re-check surfaced that are worth stating plainly rather than burying:

1. **R5 was a real gap.** `DESIGN.md` §3.4 says the grounding check runs over the rendered site
   without saying what "over" means. Run naively over raw HTML it flags `#0a0a0a`, `1.5rem` and
   `0.3s` on the first honest page — and a check that cries wolf every run is a check that gets
   disabled, which would silently remove Principle VI. Deciding scope per kind, in code, once,
   is what keeps the derivation set from being quietly widened to absorb false positives.
2. **R4 turns a stub into an adapter.** Writing the publish sink as an in-process function call
   would make `execute()` and `verify()` read from the same transaction — the "status field is
   not evidence" failure in miniature. Going over HTTP to something the adapter does not share a
   process with is what makes the pair honest.

**Structure Decision**: one repository, one installable Python package, three sibling trees with
their own toolchains ([research.md R1](./research.md)). `web` and `worker` are the same image
with different commands, so splitting the Python into two distributions would create a packaging
boundary the deployment does not have. `prompts/` sits outside `epyhia/` deliberately: Principle
I's enforcement is a CI check that scans that directory as a directory, and burying it inside the
package invites someone to reach for an f-string next door and stay technically compliant.

The ordering inside `epyhia/` mirrors the build order rather than alphabetising: `gate/` is
first because it is step 2 and has no upstream dependencies at all — *the door before the rooms*.
